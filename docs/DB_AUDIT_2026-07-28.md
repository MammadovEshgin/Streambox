## Verdict

The schema design is sound — ownership model is consistent, `auth.users` cascades are complete,
RLS is on for every `public` table, and the social-platform teardown (`20260728090000`) is clean
with zero leftovers. The problems are not in the design; they are in **drift between the migration
files and the live database**, and that drift has already broken two write paths in production.

| Severity | Count | Headline |
|---|---|---|
| **P0 — broken now** | 2 | Library + watch-history sync RPCs return HTTP 300; daily-recs table is empty |
| **P1 — security** | 7 | Anon-readable RLS-bypass view; DEFINER functions callable by anon; over-broad grants; unbounded storage bucket |
| **P2 — perf/hygiene** | 7 | 35 RLS initplan re-evals, duplicate/unused indexes, no telemetry retention |
| **P3 — process** | 2 | Migrations cannot rebuild this database |

## P0 — Broken in production right now

### P0-1 — Every media-library and watch-history sync write fails with `PGRST203`

`public.sync_streambox_media_library_item` has **three** overloads, and two of them have an
*identical set of parameter names* (differing only in order):

```
DEFINER  (p_operation, p_list_kind, p_media_type, p_tmdb_id, p_imdb_id, p_collected_at, p_snapshot, p_audit_metadata, p_internal_id)
INVOKER  (p_operation, p_list_kind, p_media_type, p_tmdb_id, p_internal_id, p_imdb_id, p_collected_at, p_snapshot, p_audit_metadata)
```

PostgREST resolves RPCs by *name set*, not order, so it cannot choose. Same situation for
`sync_streambox_watch_history_entry` (21-arg, and two 22-arg variants sharing a name set).

`src/services/userDataSync.ts:848` and `:853` **always** send `p_internal_id` (as
`ids.internal_id`, `null` included). So every call matches both candidates.

**Verified live** against the REST API:

```
POST /rest/v1/rpc/sync_streambox_media_library_item   → HTTP 300
{"code":"PGRST203","message":"Could not choose the best candidate function between: ..."}

POST /rest/v1/rpc/sync_streambox_watch_history_entry  → HTTP 300  (PGRST203)
```

`delete_streambox_watch_history_entry` is **fine** — its two overloads have different name sets
(3 vs 4 params) and the app sends 4, so it routes correctly (probe returned `22P02`, a type error,
meaning it reached the function).

**Choosing which overloads to drop is a product decision, not a mechanical one.** The two families
behave differently:

| Overload | Audit logging | Conflict target |
|---|---|---|
| DEFINER, `p_internal_id` **last** (3561 / 4748 chars) | ✅ writes `user_audit_logs` | partial-index era |
| INVOKER, `p_internal_id` **5th/3rd** (1226 / 1002 chars) | ❌ **no audit logging** | uses the `coalesce(...)` sync index |
| INVOKER, no `p_internal_id` (3146 / 3019 chars) | ✅ | pre-`internal_id`, unreachable from the app |

The short INVOKER pair is the newer hand-written implementation (it targets
`idx_user_media_library_sync`, a prod-only index), but it silently dropped the audit trail. Decide
which behaviour you want, then drop the other two of each family. Whichever survives must also get
`set search_path` (see P1-3).

### P0-2 — `user_daily_recommendations` writes fail with `42P10`; table is empty

`src/services/userDataSync.ts:860` upserts with a **4-column** conflict target:

```ts
onConflict: `user_id,recommendation_kind,recommendation_date,${ids.tmdb_id ? 'tmdb_id' : 'internal_id'}`
```

The only matching unique indexes are **partial**:

```sql
user_daily_recommendations_tmdb_unique     ... (user_id, recommendation_kind, recommendation_date, tmdb_id)     WHERE tmdb_id IS NOT NULL
user_daily_recommendations_internal_unique ... (user_id, recommendation_kind, recommendation_date, internal_id) WHERE internal_id IS NOT NULL
```

Postgres only infers a partial unique index for `ON CONFLICT` when the conflict clause repeats the
index predicate — which PostgREST's `on_conflict=` never emits. Result: `42P10`, guaranteed.

Corroborating evidence from prod: the table has **0 live rows**, and all three of its unique
indexes have `idx_scan = 0` (never used).

There is also a design contradiction: the primary key is the **3-column**
`(user_id, recommendation_kind, recommendation_date)`, which already permits only one row per
user/kind/date — making the 4-column uniques redundant by construction.

**Fix (app side, one line):** send the 3-column target `user_id,recommendation_kind,recommendation_date`,
matching the PK. This was flagged as F2 on 2026-07-02 and is still live.

## P1 — Security

### P1-1 — `external_ratings_active_alerts` bypasses RLS and is readable by anon — **verified**

The view has no `security_invoker` option, so it runs as its owner (`postgres`) and bypasses RLS on
its base table. It is also granted `ALL` to `anon` and `authenticated`.

```
anon GET /rest/v1/external_ratings_active_alerts  → HTTP 200  []
anon GET /rest/v1/external_ratings_function_logs  → HTTP 401  42501 permission denied
```

The base table correctly denies anon; the view hands the same data over anyway. It returns empty
**today only because `external_ratings_function_logs` currently has 0 rows**. As soon as the ratings
edge function logs anything, unauthenticated callers can read `error_message`, `imdb_id`,
`status_code`, `latency_ms` and `metadata`.

```sql
alter view public.external_ratings_active_alerts set (security_invoker = on);
revoke all on public.external_ratings_active_alerts from anon, authenticated;
```

`admin_user_directory` is also a definer-semantics view, but it has **no** anon/authenticated grants
(service_role only), so it is not exposed. Still worth setting `security_invoker` for consistency.

### P1-2 — Unauthenticated callers can invoke `SECURITY DEFINER` maintenance functions — **verified**

These are `SECURITY DEFINER` and carry the Postgres default `EXECUTE` grant to `PUBLIC`, which
`anon` inherits:

- `capture_external_ratings_alerts()` — writes alert rows
- `cleanup_external_ratings_monitoring(integer)` — **deletes** monitoring data by retention window
- `ensure_external_ratings_jobs()` — manipulates `cron.job`
- `get_hot_external_ratings_candidates()` — reads cache internals
- `rls_auto_enable()` — event-trigger function

Confirmed reachable with the anon key and no JWT:

```
POST /rest/v1/rpc/get_hot_external_ratings_candidates  → HTTP 200  []
```

The destructive ones were **not** executed, but they carry the identical grant and exposure. These
are cron-only internals and should never have been REST endpoints.

```sql
revoke execute on function public.capture_external_ratings_alerts()            from public, anon, authenticated;
revoke execute on function public.cleanup_external_ratings_monitoring(integer) from public, anon, authenticated;
revoke execute on function public.ensure_external_ratings_jobs()               from public, anon, authenticated;
revoke execute on function public.get_hot_external_ratings_candidates()        from public, anon, authenticated;
revoke execute on function public.rls_auto_enable()                            from public, anon, authenticated;
```

(`rls_auto_enable()` would error out if called directly — it needs an event-trigger context — but it
should not be routable at all.)

### P1-3 — `SECURITY DEFINER` + mutable `search_path`, granted to anon

Six functions trip `function_search_path_mutable`. The dangerous combination is DEFINER **and** no
`search_path` **and** anon-executable — which applies to all three sync/delete RPCs:

- `sync_streambox_media_library_item` (9-arg DEFINER)
- `sync_streambox_watch_history_entry` (22-arg DEFINER)
- `delete_streambox_watch_history_entry` (4-arg DEFINER)

Whichever overloads survive P0-1 need:

```sql
alter function public.<fn>(<sig>) set search_path = public, pg_temp;
revoke execute on function public.<fn>(<sig>) from anon;   -- authenticated-only RPCs
```

These functions already gate on `auth.uid() is null → raise exception`, so anon cannot do damage
today — but the anon grant is unnecessary surface, and DEFINER-without-search_path is the standard
escalation shape.

### P1-4 — `GRANT ALL` to `anon` on seven tables

`watch_rooms`, `watch_room_members`, `watch_room_memories`, `franchise_collections`,
`franchise_entries`, `user_franchise_progress` and the `external_ratings_active_alerts` view all
carry `DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE` for **both** `anon` and
`authenticated`.

RLS does contain the row-level damage (the watch-room policies are correct, and
`user_franchise_progress`'s `auth.uid() = user_id` evaluates to NULL→false for anon). And `TRUNCATE`
is not reachable through PostgREST. So this is **not currently exploitable** — it is a
least-privilege failure that removes your safety margin: any future table exposed this way with a
weak policy is immediately anon-writable.

```sql
revoke all on public.watch_rooms, public.watch_room_members, public.watch_room_memories,
              public.franchise_collections, public.franchise_entries, public.user_franchise_progress
       from anon, authenticated;
grant select on public.franchise_collections, public.franchise_entries to anon, authenticated;
grant select, insert, update, delete on public.watch_rooms, public.watch_room_members,
      public.watch_room_memories, public.user_franchise_progress to authenticated;
```

### P1-5 — `private.rate_limit_windows` has RLS disabled

Zero policies, `relrowsecurity = false`. It is *not* reachable — the `private` schema grants no
privileges to `anon`/`authenticated` — but it is the one table in the database without RLS, and it
relies solely on schema-level grants. Enable it as defense in depth.

### P1-6 — `watch-memories` bucket has no size limit and no MIME restriction

Both buckets are correctly **private**, and the object policies are properly scoped (`profile-assets`
by `foldername(name)[1] = auth.uid()`, `watch-memories` by `is_watch_room_member(...)`). No leftover
social/peer storage policy — the teardown was clean here too.

But the two buckets are configured inconsistently:

| Bucket | Public? | Size limit | Allowed MIME types |
|---|---|---|---|
| `profile-assets` | private | 8 MiB | `image/jpeg, image/png, image/webp, image/heic` |
| `watch-memories` | private | **none** | **any** |

Any authenticated room member can upload files of unlimited size and arbitrary type into
`watch-memories`, which only ever holds polaroid images. Unbounded storage cost, and a bucket that
will happily accept executables or HTML.

```sql
update storage.buckets
   set file_size_limit = 8388608,
       allowed_mime_types = array['image/jpeg','image/png','image/webp']
 where id = 'watch-memories';
```

`watch-memories` has no DELETE policy, but that is deliberate — deletion goes through the
`remove_watch_memory` RPC.

### P1-7 — Platform settings

- `pg_net` is installed in the **`public`** schema (advisor `extension_in_public`). Move to `extensions`.
- **Leaked-password protection is disabled** in Auth — enable HaveIBeenPwned checking in the dashboard.

## P2 — Performance and hygiene

### P2-1 — 35 RLS policies re-evaluate `auth.uid()` per row

Every policy across 13 tables uses bare `auth.uid()` instead of `(select auth.uid())`, so it is
re-evaluated for each candidate row rather than hoisted to an InitPlan. Data volumes are small today
(largest table 2,318 rows), so the cost is not yet visible — but it is a mechanical, zero-risk fix:

```sql
-- e.g.
alter policy user_watch_history_select_own on public.user_watch_history
  using ((select auth.uid()) = user_id);
```

### P2-2 — Index bloat: indexes are up to 3× the table

| Table | Rows | Heap | Indexes | Count |
|---|---|---|---|---|
| `user_watch_history` | 2,318 | 4504 kB | 2392 kB | 10 |
| `user_media_library` | 1,197 | 296 kB | **968 kB** | 9 |
| `app_telemetry_events` | 10,611 | 2512 kB | 2368 kB | 5 |

On `user_media_library` and `user_watch_history` there are effectively **three** overlapping
uniqueness schemes stacked on top of each other:

1. partial uniques (`idx_*_tmdb`, `idx_*_internal`, `WHERE ... IS NOT NULL`)
2. total uniques (`*_tmdb_unique`, `*_internal_unique`, no predicate)
3. a `coalesce(tmdb_id::text, internal_id::text)` total unique (`idx_*_sync`)

Plus `*_user_internal_lookup_idx`, which is a non-unique copy of the partial unique above it.

### P2-3 — Confirmed duplicate indexes

- `user_audit_logs_action_type_idx` ≡ `user_audit_logs_user_action_occurred_idx` — byte-identical
- `franchise_entries_franchise_order_idx` ≡ `idx_franchise_entries_watch_order` — byte-identical
- `user_episode_progress_lookup_idx` ≡ `user_episode_progress_pkey` — same four columns, same order

### P2-4 — 17 indexes have never been scanned

Largest: `app_telemetry_events_name_inserted_idx` (696 kB), `user_watch_history_genres_gin_idx`
(544 kB), `app_telemetry_events_category_inserted_idx` (448 kB), `idx_user_media_library_sync`
(168 kB). Confirm against your query patterns before dropping — `idx_scan = 0` on a young cluster
can mean "not yet needed" rather than "not needed".

### P2-5 — Unindexed foreign keys

- `watch_room_memories.room_id` → `watch_rooms` — **also used in the RLS policy predicate**
- `watch_room_memories.created_by` → `auth.users`
- `watch_rooms.host_user_id` → `auth.users` — used by the host UPDATE/DELETE policies
- `user_announcement_views.announcement_id` → `app_announcements`
- `user_settings.theme_id` → `app_themes`

### P2-6 — No retention on `app_telemetry_events` or `user_audit_logs`

`app_telemetry_events` holds 10,611 rows dating to 2026-05-14; **5,704 are older than 30 days** and
nothing prunes them. There are four `pg_cron` jobs, but only `external-ratings-monitoring-cleanup`
prunes anything, and it only covers the ratings tables. Telemetry and audit logs grow unbounded.

### P2-7 — Write amplification and bloat

`user_watch_history` has recorded **219,646 updates against 2,318 live rows** (~95 rewrites per row),
each of which must maintain 10 indexes. Worth tracing the sync loop — that ratio suggests repeated
no-op writes.

Dead-tuple ratios: `watch_room_members` 4 live / 26 dead, `watch_room_memories` 25 live / 17 dead,
`user_audit_logs` 26%, `franchise_collections` 36%. Small in absolute terms; these tables are simply
too small to trigger autovacuum thresholds.

*Unverified, worth checking:* `user_announcement_views` shows `n_tup_ins = 0` — no row has ever been
written, despite `announcementsService.ts:282` upserting into it (its conflict target *does* match
the PK correctly). Either the path is dead code or something upstream is failing silently.

## P3 — Process: the migrations cannot rebuild this database

This is the root cause behind P0-1 and P0-2, and the most important thing to fix.

**Three tables exist in production with no `CREATE TABLE` anywhere in `supabase/migrations/`:**
`franchise_collections`, `franchise_entries`, `user_franchise_progress`.

They are only ever *referenced* — `20260605130000_complete_james_bond_collection.sql:135` does
`insert into public.franchise_entries (...)`. A clean `supabase db reset` therefore **fails**: the
seed migration inserts into a table that was never created.

**Objects that exist only in production, hand-created in the SQL editor:**

- `idx_user_media_library_sync`, `idx_user_media_library_tmdb`, `idx_user_media_library_internal`
- `idx_user_watch_history_sync`, `idx_user_watch_history_tmdb`, `idx_user_watch_history_internal`
- `user_daily_recommendations_{tmdb,internal,none}_unique`
- `idx_franchise_*`, `idx_user_franchise_progress_user_id`
- the `p_internal_id`-carrying overloads of all three sync/delete RPCs — **this is exactly how the
  P0-1 collision was created**: a new overload was added by hand without dropping the old one

**Direct contradictions between file and reality:**

`20260319_add_internal_id_sync_support.sql` declares `user_media_library_tmdb_unique` and
`user_watch_history_tmdb_unique` as **partial** (`where tmdb_id is not null`). In production both
are **total** (no predicate). Verified via `pg_index.indpred IS NULL`.

Consequence: prior audit finding **F1** ("PostgREST cannot infer partial unique indexes for
`on_conflict`") is *resolved in production* — by hand-made total indexes — but **not in the
migrations**. Rebuilding from files would silently reintroduce it.

There is also **no `supabase/config.toml`** in the repo, so project settings are not versioned
either.

**Recommended sequence:**

1. `supabase db dump --linked --schema public > supabase/schemas/public.sql` to capture reality.
2. Write one reconciliation migration containing the three missing `CREATE TABLE`s and every
   prod-only index, ordered *before* the Bond seed — or squash history to a single baseline.
3. Fix P0-1/P0-2 in that same migration.
4. Verify with `supabase db reset` on a local/branch database that a clean replay succeeds.
5. Commit `config.toml`.

Until step 4 passes, treat every `db push` as unsafe.

## What is healthy

- **RLS is enabled on all 21 `public` tables**, and the ownership predicates are correct throughout
  (`auth.uid() = user_id`, `id = auth.uid()`, or `is_watch_room_member(...)`).
- **Every `UPDATE` policy has both `USING` and `WITH CHECK`** — no user can reassign a row to
  another user. This is the trap most projects fall into.
- **No `TO public`-with-`true` policy on any user-keyed table.** The three `TO PUBLIC` policies
  (`franchise_*`, `provider_configs`) are on genuinely global catalogue data.
- **`auth.users` cascade coverage is complete** — all 14 user-keyed FKs are `ON DELETE CASCADE`
  (or `SET NULL` for telemetry, which is deliberate). No orphan risk on account deletion.
- **The social-platform teardown is clean.** Zero leftover tables, functions, enums or columns
  matching `follow|social|peer|feed|username|public_profile`. `20260728090000` did its job — and it
  *is* applied on prod, contrary to the note in project memory.
- **`private` schema is properly sealed** — no `anon`/`authenticated` grants.
- **Write paths that do work are correct:** `delete_streambox_watch_history_entry`,
  `sync_streambox_episode_progress`, `sync_streambox_profile_and_settings`,
  `get_my_streambox_bootstrap` and the watch-room RPCs all route and are `authenticated`-scoped.
- **No secrets embedded in `cron.job.command`** — the ratings refresh job references its key by
  name, not by literal.
- Realtime publication `supabase_realtime` carries **no tables**, consistent with Watch Together
  using broadcast/presence signalling rather than Postgres CDC. Nothing is leaking over CDC.
